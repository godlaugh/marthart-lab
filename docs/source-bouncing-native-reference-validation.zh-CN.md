## 实际 draw 与稳定帧（更正及新增证据）

第四次原生运行耗时 7.823 秒，在 `glDrawArrays(GL_POINTS)` 调用前记录状态，在调用后读取实际 draw framebuffer 并恢复 read framebuffer。原方法照常执行，未改写 shader、uniform、粒子或绘制参数；对应的三张完整帧摘要与前三次运行一致。退出、设置/许可检查和进程回收均通过。

首个点 draw 的 viewport 为 `[0,0,0,0]`，后两次为 `[0,0,500,600]`。稳定帧 raw SHA-256 为 `817665ec678ad1a38313b6d550851452a7214df24ae8a7116fc69b29e1c96893`；增强图为 `51e82b5a8697984929b4c044fcee1ee86e7109ed0904a94b3b8cbc992ea22db8`。不能把首帧空图作为产品目标，也不需要修改原版初始化规则。

使用完整 200 万生产种子和同一相机进行单变量控制：只把物理高度产生的点大小缩放除以像素密度 2，固定 ROI `[55,55,445,510]` 的 RGB 与稳定原生 raw 完全一致。原比例的独立重放在该 ROI 与旧产品 PNG 的 RGBA 完全一致，建立了前后桥接。诊断粒子框 `[120,180,375,420]` 与原生点 draw 的 RGBA 也完全一致；该框仅用于定位，不替代固定 ROI 或整图验收。

原生点 draw 的 alpha 与最终 raw 不同。进一步检查原包 Processing 4.5.0 字节码：`PGraphicsOpenGL.endOffscreenDraw` 在 `backgroundA == 1` 时只清 alpha 通道为 1，再恢复 color mask；`readPixels` 使用保留 alpha 的 `nativeToJavaARGB`。因此不透明处理属于完成离屏绘制的步骤，不能归因于 PNG 编码或无条件把透明背景改为不透明。静态 PNG 随后还需共用 `buildEnhancedImage` 对应的增强步骤。

新增本地证据：`draw-intercept/`、`comparison-stable.json`、`radius-control/`，均位于上述缓存目录。原版水印、字体及整图仍应分开报告；零误差区域不代表完整场景验收通过。


## 正式流程修复与本轮结果

实测 renderer 密度由 App 请求传入，生成会校验物理尺寸等于逻辑尺寸乘密度，并随已呈现帧交付；导出继承该帧事实，使用共同暂停捕获尺寸规划。缺少密度会拒绝，作品中不持久化运行时密度，也不假定所有设备为 2。密度 2 下，请求 321×181 会按原规则生成 322×182，计划同时保留用户请求值；视频服务接收明确的输入物理尺寸。没有为视频引入尚无原生证据的额外倍率。

GPU 完成目标时按背景 alpha 条件执行原版的 alpha-only clear，不改变已混合 RGB；所有消费者共用同一输出。静态 PNG 随后通过已有可取消 Worker 执行增强，保留原始帧，不伪造当前图像捕获身份。视频不执行暂停 PNG 增强。

重新构建后，实际页面导入原始 200 万粒子文件，等待初始暂停帧，以 500×600 导出。确认 preview/export 密度均为 2、输出逻辑尺寸 250×300、更新次数仍为 0、增强 Worker 完成、页面无错误。PNG SHA-256 为 `cae4db39d8d89ea0b1e9f14b26dc70edd0caf4c4f56a1947872b6cfdfd11af3d`。

相关 20 项导出/生成测试通过。真实 Chrome 的公开生成与 Worker 24 个图像案例、6 个预期失败案例通过，覆盖密度切换不推进模拟、不透明及半透明背景。独立提取 shader 并补齐原包 Processing 目标结束规则的浏览器参考，72 个 framebuffer、657,108 像素逐字节一致，180 份状态比较及 7 个预期失败通过；资源清理归零。这组参考仍属同浏览器 GPU 验证，不冒充原生窗口对照。
