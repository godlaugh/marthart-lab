# 域着色：逻辑画布与 Retina 像素

本轮修正了明确密度目标下的渲染方式：完整源 CPU 链先计算逻辑尺寸的 RGB 图像，再通过实际 WebGL LINEAR／CLAMP_TO_EDGE 纹理呈现到物理画布。源 GPU 链保持物理像素采样，单独接收逻辑分辨率。没有把 GPU 规则的 CPU 数值参考误当成原版 CPU 图像。

这是当前帧 PNG 接入的前置修正。**主界面尚未启用 Domain 实时会话，当前状态 PNG 和录制仍待接入，原版整窗一致性仍为 0/11。**

## 可见差异

原版共享保存尺寸规则会按像素密度取整。例如请求 161×121、密度 2，实际逻辑画布为 81×61，物理图像为 162×122。完整 CPU 链计算 4,941 个样本；GPU 链计算 19,764 个物理样本。将 CPU 直接按物理尺寸重新求值，会改变图案细节，不只是清晰度。

显式目标现在由一个边界验证并传入 Worker。尺寸与密度不一致时拒绝请求；不会悄悄缩小逻辑采样格。没有显式目标的旧预览仍保留原有自适应尺寸，密度 1 的像素回归保持一致。

渲染结果记录逻辑尺寸、物理尺寸、密度、采样方式和实际呈现后端。CPU 公式配合 GPU 纹理呈现时，公式后端仍准确记为 CPU。全链 GPU 失败后的 CPU 回退同样采用逻辑图像，并继续保留此前的失败状态。

## 独立验证

实际 Generator／Worker 在无界面 Chrome 中执行密度 1、2、3 的四组目标，覆盖奇数请求取整和跨 GPU 分块边界。独立 WebGL 程序上传逻辑 RGB 图像，使用 LINEAR 纹理过滤、CLAMP_TO_EDGE 与物理尺寸读回，与生产结果逐字节比较。源 GPU 则与相同物理尺寸、等价宽高比的既有生产路径比较，防止错误缩小 GPU 采样格。

开发过程中，纯软件双线性插值在密度 2／3 的少量通道与实际 WebGL 相差 1 个色阶。没有将这一差异作为成功结果放行；生产路径改为真实 GPU 纹理呈现，最终四组比较均为零差异。设备图形能力不可用时才使用软件回退，并在结果与警告中明确标记；软件回退不声称原版逐字节一致。

资源所有者沿用 Domain 的 GL 上下文、程序缓存与失败清理机制。测试覆盖编译、链接、分配、framebuffer、绘制、读回、上下文丢失和取消后的资源释放。物理结果与逻辑 CPU 中间图合计最多 128 MiB；纹理呈现还可能需要同等上限的 GPU 纹理及最多一行（64 KiB）的翻转缓冲。该限制不包含驱动、程序或进程的全部开销。

## 证据范围

逻辑 CPU 图像与过滤规则依据固定 MathArt 1.7.8／Processing 4.5.0 字节码、方法调用和纹理状态。MathArt JAR SHA-256 为 `a6e1da3acfc05c347d2529c1d590657e2dd798e16d38c55df3dc61312be24018`，Processing core JAR 为 `89410e2c4f59cb4b4aeb2a3baeaf6a4bc189d6e1c612920c3f8e0f58b62a769a`。

独立 WebGL 比较证明本地纹理呈现与已确认的 LINEAR 规则相符，不证明原应用 JOGL 驱动的完整图像一致。原版窗口、公式叠加、PNG 增强及 3／5 倍放大仍需在最终保存流程中验证。本轮没有操作桌面或替换已安装的 1.0 应用。
