# 曲面实际帧率输入与原版数值对照（2026-10-22）

本轮确认并修复了曲面更新内核的一个缺口：参数动画原先只能使用构造时的固定帧率，无法消费每帧实际观测值。现在 CPU/GPU 点和网格的更新通路均能接收独立的 `actualFrameRate`，缺省时保留明确的固定回放输入。**曲面的 App 实时场景时钟尚未接入；原版整窗口一致性仍为 0/11。**

## 原版实际执行结果

使用原 MathArt 1.7.8 安装包内的 JVM、`ParametricSurface.update`、`MeshSurface.update`、`SurfaceParameterAnimator` 和 `JsonSurfaceFunction` 执行了 12 组、120 次更新。整个探针执行两次，结果相同，两个 JVM 子进程均正常退出并回收，stderr 为空。

观察到：

- 参数动画读取当帧 `PApplet.frameRate`，与传入的时间步长是两个输入。
- 37、24、29.97、120、500 FPS 均按观测值消费；500 不应被配置帧率的 120 上限截断。
- 观测 FPS 不大于 1 时，原参数动画内部改用 60。
- `dt` 为零或负数时，曲面对象提前返回，不更新参数或对象动画时间。
- 空网格也提前返回。此边界保留为原版观察；本地网格配置要求正采样数，不把空网格视为本地支持项。
- 负步进、初值超出范围和极窄范围都使用原方法执行，没有用另写的公式代替原方法。

例如初值 a=0.25、step=0.1、范围 [-1,1]：以 dt≈0.1、实际 37 FPS 更新后 a≈0.583214477；再以 dt≈0.2、24 FPS 更新后 a≈0.892419917。后续零／负 dt 保留该值。对应的本地内核改动前固定使用 4 FPS，12 组生产对照失败；改动后全部通过。

## 实现与验证

实际帧率的解释集中在 `sourceSurfaceFrame.ts`，点和网格共同使用它。`SourceSurfaceHost` 与 GPU 点包装器保留并传递该字段，参数动画仍由既有注册表负责，不复制第二套振荡计算。非有限值、Float32 溢出及错误类型明确失败；失败的宿主保持失败状态。零 dt 不消费观测值。旧固定回放不提供观测时继续使用原帧率，作品数据不被迁移。

| 验证 | 实际结果 |
| --- | --- |
| 原 JVM 执行 | 12 组 × 10 次更新，重复两次相同；约 0.92／0.35 秒，属于局部执行时间而非受控冷暖基准 |
| 新生产边界测试 | 29 项通过；四种 CPU/GPU 点/网格输出、原双精度相位、非法观测、零 dt 和固定回放兼容 |
| 相关集成测试 | 6 个文件、111 项通过 |
| 完整测试 | 403 个文件、7,596 项全部通过 |
| TypeScript 与生产构建 | 通过；既有 bundle 体积提示仍在 |
| 固定回放改动前后 | CPU/GPU × 点/网格，32×24、每任务 31 帧、每种各 3 次，全部几何或 GPU 数据快照摘要一致 |

原双精度参数和相位保留 13 位小数比较容差，用于 Java Math 与 JavaScript 数学库的末位差异；最终几何与 GPU uniform 的 Float32 值逐值精确比较。负原始 dt 在局部测试中显式映射为零 activeDt，这不表示完整实时场景时钟已经实现。

GPU 检查覆盖生产的参数、种子和几何数据交付，**本轮没有执行 GPU 着色器或绘制原版画面**。原探针跳过图形构造，JNI 分配 PApplet/Surface/Mesh，调用原函数／参数动画构造与实际 update 方法；函数表达式未参与求值，Mesh 使用占位或空数组，未执行 Scene 队列、GL、窗口和视频编码。因此不能据此声称原应用完整生命周期已验收。

## 成本与复核

改动前基线为 `5493f46d2b9f91fbbaa96ec988200d4d8c3e496a`。四种等价固定回放任务按独立进程串行执行；每个进程在模块载入后执行一次首任务、两次使用新宿主的热运行。任务包含构造、参数动画、31 次更新／显示和完整输出摘要，不含浏览器、着色器、PNG 或 App 启动。

| 任务 | 改动前首／热运行耗时 ms | 改动后首／热运行耗时 ms |
| --- | --- | --- |
| CPU 点 | 15.00／9.04／5.62 | 15.42／9.24／6.58 |
| CPU 网格 | 36.60／26.94／20.81 | 36.61／27.62／21.31 |
| GPU 点数据 | 8.66／2.35／1.89 | 9.77／2.27／1.97 |
| GPU 网格数据 | 14.31／7.01／4.46 | 13.61／6.74／4.30 |

各子任务 CPU 时间和累计 maxRSS 保留在原始记录中。整个比较任务观测墙上时间 1.02 秒、进程族 CPU 时间 0.65 秒、峰值聚合 RSS 135.16 MiB，未观测到遗留的所属进程。50ms 采样遗漏了一些短命子进程，因此外层 CPU 数字不是完整总量；RSS 可重复计入共享内存。没有测量完整 App 冷暖任务、token 或显存，也不据此宣称性能提升。

原版复核入口为 `scripts/source-surface-clock/run.py`，需要用户已持有的原应用和现成 JNI 头文件目录；它不安装依赖，拒绝不同 JAR 摘要，要求新的输出目录，单个原 JVM 子进程限时 45 秒。文本证据及方法限制保存在 `tests/fixtures/source-surface-clock/`，探针源码一并保留。
