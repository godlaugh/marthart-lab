# Map／Symmetry 公开录制与视频编码验证

2026-10-21。Map、Symmetry 已接入“按源完成条件录制”：从最后应用的配置开始，丢弃一个预热帧，到队列完成时停止提交新帧；录制画面显示在主预览，等待编码器完成后恢复实时播放。保留“按时长导出”作为独立模式。**这仍不是原版完整窗口效果验收，2.0 仍处于 M3，整窗口对照为 0/11。**

## 行为与原包依据

固定 MathArt 1.7.8 JAR SHA-256：a6e1da3acfc05c347d2529c1d590657e2dd798e16d38c55df3dc61312be24018。重新核对 VideoRecorder、MathArt、MathArtConfig 和质量设置 UI 的当前类字节；完整方法偏移、类哈希与字符串模板保存在 .cache/source-map-lifecycle/recording-encoder-audit.md。

原版把请求尺寸乘以 Float32 的 3，再按主画布的像素密度舍入，得到输入缓冲区。VideoRecorder 单独把奇数输出尺寸减一，然后在输入与输出尺寸不同时添加 Lanczos 缩放。现在界面与录制核心共用输入尺寸所有者；编码服务独立保存输入、输出尺寸，检查上传 PNG 与输入尺寸完全一致，两个尺寸都纳入资源预算。

例如本轮请求 97×65：密度 1 的输入为 291×195；密度 2 的输入为 292×196；最终视频均为 96×64。界面会显示实际输出尺寸。暂停 PNG 的增强与放大不会进入视频链路。

原包只提供 MP4/H.264。新录制的 MP4 配置保留 yuv444p、完整范围 pc、bt709 色彩空间／原色、sRGB transfer 参数及 faststart+write_colr。四档质量如下，默认采用 MathArtConfig 的 high；原版偏好、启动参数和权限 UI 可以改变其默认，本地没有声称读取了这些外部设置。

| 质量 | Preset | CRF | Tune |
|---|---|---:|---|
| low | veryfast | 28 | 无 |
| medium | medium | 23 | 无 |
| high | slow | 18 | animation |
| production | veryslow | 10 | animation |

本地 WebM／GIF 继续作为扩展格式使用已有编码器，尺寸不同时共用 Lanczos 缩放；不将它们描述为原版功能。既有 Perlin 和普通视频的默认编码配置保持原有行为。

## 状态交接

App 停止录制时同步运行时返回的新会话、重播版本、时间和播放状态，不再一律暂停。消费者只呈现已经生成的录制图像，没有为预览额外推进一次模拟。模拟与编码使用同一个帧率；共享队列提供编码完成回调，正常完成时先等待 FFmpeg 收尾确认，才释放固定步长运行时。取消和编码请求失败仍先释放录制所有者，恢复主预览，再清理编码服务。切换到其它场景后，旧录制的收尾不能覆盖新场景。

录制核心和界面共享三倍输入尺寸函数；Perlin、Map、Symmetry 共用导出消费代码，没有新增另一套 PNG 上传和取消处理。

## 实际验证

- 两个场景共 12 个实际 App／Worker／WebGL 工作流：正常 MP4、取消上传、注入帧请求拒绝、注入编码结束响应失败、关闭导出窗口并切换场景、空队列。Map 使用实际密度 1，Symmetry 使用实际密度 2。
- 实际请求 97×65，核对三倍输入舍入后逐帧 PNG 的完整 RGBA 与 Worker 一致，预热不上传；视频解码确认输出 96×64、3 帧、4 fps，并检查画面非空、帧间发生变化。
- 正常完成时验证全部录制图像进入主预览；阻挡真实编码成功响应后检查运行时不会提前恢复。编码结束后同一 Worker／会话继续播放，并可暂停。切换场景后旧结果不覆盖新场景。
- 编码服务 24 项检查通过，包括 MP4／WebM／GIF 缩放、错误输入尺寸不消费帧、输入像素预算、非法质量／格式拒绝、已有取消／资源清理用例。四档 MP4 的完整 RGB 解码结果与独立原包 rawvideo 参数命令一致。

既有 Perlin 的 5 个公开录制流程通过；Map／Symmetry 原有按时长导出、PNG、编辑／保存／重新打开 2 个工作流通过。完整测试通过 352 个文件、6641 项检查。最后仅隐藏了新录制模式中不适用的“固定时间重放”说明，之后重新执行 Web 构建与 12 个 Map／Symmetry 公开流程；未因此重复无关测试。

## 发现与限制

最初的小样本自定义公式能够验证传输和状态，但编码结果全黑，因此没有作为可见画面验收。最终改用固定原包的 Clifford_deJong_2D_3 与 Emperors_Cloak 项目，明确覆盖 batch_size=512、burn_in_steps=32、iterations_per_frame=16、dot_size=6 和一秒 Wait 队列；关闭文字覆盖。加入完整解码帧的非均匀性与帧间变化断言，保留原包成员哈希及完整测试输入。

独立原包审查还发现初版允许模拟／编码独立帧率，并在编码收尾前恢复实时。两处均已按原版修正；成功录制的公开验证会实际完成服务端编码，再暂缓交付完成响应，确认此期间运行时没有提前停止或恢复实时。

第一次公开流程探测在暂停后要求最后一张图像带 paused=true，误把播放控制当作必须额外绘制一帧。产品的暂停确认不推进图像；验证改为检查实际播放确认、新会话保持及后续状态。

本机 ffprobe 返回 yuvj444p、pc、bt709，但没有返回 transfer 和 primaries。直接使用原包 rawvideo 参数独立编码，得到同样结果。因此本报告只把这些参数视为命令意图，不声称文件保留了全部颜色标记。四档质量另外比较独立 raw RGBA 命令生成的视频与服务端 PNG 输入视频的完整解码帧；这能验证本机的传输／编码一致性，不代表已执行原版 Java／JOGL 渲染。

DPR 2 的首次探测使用低预览质量，实际画布密度被限制为 1；原本期待密度 2 的尺寸断言失败。最终改用标准质量检查实际密度 2，并保留独立的密度 1 案例，未改产品的密度策略。

仍有明确边界：输入沿用当前源画布物理像素预算（最多 16,777,216 像素），三倍输入可能使较大的输出请求被预检拒绝；没有自动降低倍率或替换编码路线。高分辨率和大量粒子性能未在本轮验收。Map／Symmetry 的结构设置 Apply 暂存、部分参数热更新／相机编辑时机，以及所有场景的原版完整画面对照仍待完成。Apple Silicon 1.0 已安装应用未重打包；本轮只构建 Web 开发版本，未操作用户主屏。
