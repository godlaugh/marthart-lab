## 两处边界的纠正

**录像尺寸。** 原版 `ensureRenderBuffer()` 使用默认 `exportScaleFactor=3`，先以 Float32 相乘，再按实测像素密度除法和 Java round 计算逻辑尺寸。原版 VideoRecorder 随后使用 Lanczos 缩小至请求尺寸。

本地 Bouncing 导出规划此前同时对 PNG 和视频采用暂停截图尺寸。以本次请求为例，旧规划返回 128×96，原版实际为 384×288。保留旧提交的规划代码单独运行，也重现了这一差异。

现在视频复用已有 `sourceRecordingSize` 尺寸计算，PNG 继续采用暂停截图规则。逻辑投影、原始像素和服务端输入尺寸都由同一规划提供；编码器输出仍为用户请求尺寸。共享尺寸函数允许拥有者传入其既有像素预算，Bouncing 的 128 MiB 上限未扩大，其它场景的默认预算未改变。超预算会明确失败，不降低渲染倍率。

**原版活动帧采集顺序。** 旧探针在离屏缓冲已经开始绘制后调用 `runFrame`，其中粒子更新访问主画布 PGL，造成活动 draw 的 viewport 为 0×0。新探针按原版 `MathArt.draw` 顺序，先 `Scene.update(false)`，再开始离屏缓冲并调用 `Scene.render`。每帧实测 viewport 为完整 384×288，更新计数和粒子数也正确；不再用暂停重绘代替活动录像帧。

离屏宿主为新分配的 Processing graphics 绑定 JOGL 上下文，除此之外尺寸、场景和编码方法均执行原实现。第一次缺少上下文绑定、第二次诊断截图索引错误的失败记录均保留；正式参考要求完整 draw 记录且原版日志无 ERROR，不能只凭进程退出 0 判定有效。

## 视频对照具体证明什么

产品实际 Generator 与原版每个活动帧的**完整艺术 RGB**比较，参考取自正常品牌绘制之前；最终不透明 alpha 另行核对。没有裁剪区域或放宽误差阈值。

编码器检查则把原版完成帧（包括原版品牌）原样交给本地导出服务，比较服务生成的视频与原版 VideoRecorder 实际生成的视频。四个预设共 12 个编码帧，解码 RGB 全部相同；原版传给编码器的 RGBA 也与其完成 PNG 逐字节一致。两边使用同一显式选择的 FFmpeg。

这证明了所测输入的编码传输、参数和缩小路径一致，**不代表产品生成了原版品牌叠加，也不宣称两个 MP4 容器文件逐字节相同**。原版窗口交互和完整长视频仍未验收。

## 实际界面与回归

在真实 App 中，百万粒子公式预设和 500 万粒子预设各通过 **87 项**检查：PNG、当前状态／高质量 MP4、种子状态／制作级 MP4、恢复预览、继续播放、延迟清理、清理失败重试和文件保留。视频请求 256×192，实际上传 768×576 原生帧，再缩小编码。每个上传 RGBA 字节均与 Generator 输出相同，解码结果与独立原版参数编码相同。

有损误差检查现在在相同输出网格上进行：先独立缩小未编码 RGB，再与 MP4 解码 RGB 比较；仍保留 6/255 平均误差阈值。不能直接把缩小后的像素与原始 3 倍图上另一个位置的像素比较。

8 个相关测试文件、149 项测试通过；24 项实际原生生命周期检查、6 项捕获前拒绝检查通过；`build:v2` 通过，Vite 阶段 9.96 秒，仍有已有的大 chunk 提示。所有完成流程的原生资源和子进程已回收。

最终完整比较（含浏览器、参考读取、逐像素检查和编码）用时分别为 5.73、11.55、7.56、7.21 秒；采样进程族 CPU 约 11.49、19.64、12.53、12.29 秒，峰值 RSS 约 2400、2203、1830、1831 MiB。采样可能遗漏瞬时峰值；未测等价的修复前性能、严格冷暖、GPU／VRAM或 token 成本，不作加速结论。
