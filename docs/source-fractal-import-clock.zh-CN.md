# 分形导入与时间线验收（2026-10-24）

**上一轮留下的 3 个分形时间线测试失败已解决：原版运行证据确认是旧测试预期过时，当前产品实现无需修改。** 本轮保留 Mandelbrot 和原来的失败输入，改为直接比较原版逐帧记录，没有换成其他公式或放宽误差要求。

## 三个失败的原因

| 旧测试假定 | 原版实际运行结果 |
| --- | --- |
| 初始 `fractal.center_hi_lo` 设置高低位中心 | 初始配置只读取 `center`；单独提供 `center_hi_lo` 时中心为 0。高低位数组用于时间线目标，原始输入仍保留在项目来源中 |
| 等待 1 秒，再缩放 2 秒，在显示时间 2 秒恰好到达动画中点 | 30 fps 固定回放在时间 0 显示第一次更新；片段按 Float32 时间逐帧推进。时间 2 秒选择第 60 号显示帧（第 61 次更新），中心 X 为 -0.9165537340112456、zoom 为 10.797759724524258 |
| 两段各 1 秒的缩放，在显示时间 1 秒仍停留在第一段终点 | 第一段在第 29 号显示帧已结束；第 30 号帧开始第二段，中心 X 为 1.0139711794956183、zoom 为 10.063268076071498。省略缓动时也保留原版默认缓动 |

深度缩放用例在显示时间 1 秒，原版 zoom 为 1.1659161506855841e18，中心 X 高位为 0.9915222061047858。目标低位最终仍准确到达 X = 3e-20、Y = 5e-20。

第四个对照用例同时提供 `center: [1, 2]` 与 `center_hi_lo`，确认初始高位来自 `center`、初始低位为 0；动画目标低位仍正常导入、保存和插值。这避免把「初始配置字段未被读取」误判为「高精度动画丢失」。

## 验证范围与证据

原版 MathArt 1.7.8 JAR SHA-256：
`a6e1da3acfc05c347d2529c1d590657e2dd798e16d38c55df3dc61312be24018`。

本轮在原版随附 JVM 中执行真实配置构造器、中心/缩放 getter、目标动画构建、场景队列和逐帧更新。每组执行 92 次更新，选取片段边界两侧、中点和结束后共 18 帧；4 组合计 **72 个逐帧状态及 4 个初始状态**。两个独立 JVM 进程的完整输出完全一致。

测试从公开项目导入入口进入，经过保存重开和 `sceneAtTime`，对比中心高低位、缩放、场景时间、队列位置和完成状态，再回到首帧检查向后跳转重建。Float32 时间及队列事实精确比较；Double 比较沿用已有原版时钟测试的 8 × Number.EPSILON 相对界限，低位按自身量级比较。

- [可复现样本说明](../tests/fixtures/source-fractal-import-clock/README.md)：输入、JNI 探针、原版输出节选及哈希。
- [导入与保存重开测试](../tests/timeline-import.test.ts)：过时断言由原版记录替换。
- 本地完整证据：`.cache/fractal-import-clock-20261024/`，包含两次原版输出、字节码读取、测试与构建日志。

**执行结果：9 个相关测试文件、226 项测试全部通过；`build:v2` 类型检查和构建通过。** 构建仍报告已有的大体积 chunk 提示。

这次探针绕过图形对象构造器；初始视口使用真实配置 getter 和原版 setter，映射依据另有 `applyConfig` 字节码核对。它没有执行完整 applyConfig、公式注册表重映射、GUI、GL、像素渲染或视频编码，因此不能当作原版整窗口或分形画面验收。其他数值字段是明确的探针前置状态，不冒充原版默认值。

两次原版进程约 0.45 秒和 0.36 秒，相关测试约 2.48 秒；构建器报告约 9.93 秒（不含之前的类型检查）。CPU、峰值进程族内存、GPU 和本轮独立 token 成本未测量，冷暖缓存未控制；没有性能提升结论。
