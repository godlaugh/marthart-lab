**开发版 App 已接通复根实时录制和 FFmpeg 保存。** 工具栏“录制”和“导出作品 → 动画视频”均可选择后台实时计算录制，支持自然完成、手动停止并保存、取消及保存重试。以下是最新状态；后文各阶段中“尚未接入”的描述保留为当时记录。

## 正式录制协议与导出队列（2026-10-23）

实时复根录制已经从单个引擎拥有者接入正式 `Generator → 生成 Worker → 计算 Worker / WebGL2`，并接入 `GenerationQueue.recordSource`。调用方现在可以逐帧消费真实录制输出，再停止并接回同实例主预览。**App 按钮与 FFmpeg 的未知总帧数编码尚未接入；现有界面仍使用旧视频路径。**

共享录制协议现在区分两种完成事实：其它场景保留已规划的动画队列结束帧；异步复根使用 `observed-roots-display`，不携带预测总帧数。队列消费成功显示的完成事实，继续排空积压，直到自然完成、用户停止或取消；完成的预热帧仍允许零个后续帧。消费方修改交付对象不能改写队列的完成判断。

新增客户端会话拥有录制身份、下一帧序号和最后确认的数值帧，校验固定步长、实例、像素尺寸、队列计数、相机、完成条件和公式。公式配置在录制开始时解析一次，后续只验证交付标注。预热或普通帧交付失败但后台确认仍持有录制时，句柄继续保留，允许停止；未知或错误身份不会获得操作权限。停止响应不得额外推进数值帧。录制期间排队的尺寸变化采用停止后的播放状态，避免把旧暂停状态带回已经恢复的实例。

最终验证使用生产 Vite 打包版本、独占无界面 Chrome 和真实 Worker/GPU，共 20 个场景：8 个运行用例及 12 个异常用例。异常在主线程消息边界注入，底层仍使用真实生成 Worker；它们证明协议拒绝和恢复规则，不代表原版软件曾出现这些异常。

## 实时复根录制实例与停止交接（2026-10-23）

已实现并在后台验证 `RootsNativePresentationSession` 的录制开始、连续帧和停止操作。**这一步完成引擎拥有者；公共录制协议、App 录制入口和 FFmpeg 尚未接入此新路径。** 现有界面视频导出仍使用旧顺序回放，不能把本节当作新录制功能已可在界面使用的验收。

本轮重新校验原版 JAR 的 SHA256 为 `a6e1da3acfc05c347d2529c1d590657e2dd798e16d38c55df3dc61312be24018`。读取字节码确认了工具栏与底层 API 的区别：工具栏启动分支先解除暂停、调用 `resetScene`，再请求录制；底层 `startRecording` 自身只设置待启动标记。因此新录制实例会重新创建计算线程、清除旧运行历史，继续使用最后成功预览的配置。停止时只退出固定步长并重置墙钟基准，保留录制后的相机、队列和计算线程，不恢复录制前的实例。

## 应用界面接入实时复根（2026-10-23）

开发版界面现已接通后台实时复根。新导入的原版复根显式保存 `rootsPresentation.previewMode = live-worker-arrival-v1`；旧作品没有此字段时仍采用顺序回放。空间显示面板提供“后台实时采样”开关，保存/重新打开保留选择。开启时一并准备待绘制队列和完整场景队列；关闭后恢复原有时间跳转。线程准入预算取当前浏览器报告的硬件并发数，超过预算会拒绝，不静默改变作品配置的工作器数和随机分区。

暂停只停止动画时钟。应用会持续请求预览，直到计算流及积压点完成；状态栏同时显示采样进度和待绘制点数，不再让“采样完成”遮住仍在绘制的事实。播放操作等待当前显示完成、取得独立暂停/恢复确认，再继续调度。返回起点和明确重新打开创建新实例；另存为的文档标识变更仍沿用同一运行身份。实时模式没有伪造任意时刻的并发历史：界面保留返回起点，禁用时间滑块，旧顺序回放仍可跳转。

# 历史记录：修复默认点核后，颜色仍有残差

2026-10-23。已取得有效的原版密度参考，并修复产品默认绘制路径。相同原版提交数据、矩阵、点径下，20,000 和 40,000 点两个前缀的 **500×600 RGBA32F 密度图逐值相同**。这不是完整复根场景验收：最终颜色仍有少量不同，原版四线程求根到达顺序、完整样本和公开整图尚未对齐。

## 本轮实际修复

原版 `ComplexRootsMobject.ensureDensityResources` 用 `loadShader` 创建 `debugPointShader`；`PShader` 构造函数把 `glProgram` 置为 0，只有 `bind/init` 才创建并链接程序。`probePointSplatSupport` 在没有调用这两者的情况下直接读取编号。本次被动观测记录为：

```text
glUseProgram[0]
glGetUniformLocation[0, radius] => -1
glDrawArrays[POINTS, 0, 16]
glUseProgram[0]
glGetError => 1281
nonZeroCountPixels=0
selected=quad fallback
```

因此它不是一次有效的硬件点绘制能力检测。原产品主动编译并运行了这个探测着色器，Chrome 返回 812 个非零像素，于是选成了 points；这改变了原版实际路线。两种点核的覆盖面积和透明度不同，不能视为等价优化。

修复让 `mathart-1.7.8` 原生密度的 `auto` 明确采用 quad，诊断记录理由 `mathart-1.7.8-uninitialized-probe`，保留显式 points/quad 诊断入口。删除原先额外编译、绘制、整图读取的探测及其缓存状态；不在 WebGL 中制造原版的非法 GL 调用。显示层从同一个累积器读取默认选择，不再自行解释探测结果。点云模式不属于这次修改。

## 对旧失败诊断的更正

下面保留的历史记录当时尚未定位吞掉的首个异常。后续确认：**第一次探针也启用了 DebugGL**，不只是补主画布初始化的第二次。

原版 present fragment 声明标量 `float scale`。Processing `PShader.bindTyped` 把同名保留 uniform 当作 vec3 写入；实际 program 1、location 4 的类型为 GL_FLOAT，这次写入触发 1282。随后原版自己的 `presentDensity` 会用 `uniform1f` 正确写入 scale。DebugGL 提前把 GL 错误升级成 Java 异常，原版捕获异常后转入点绘制回退，改变了被测行为。

新的探针只转发调用并记录，不通过 DebugGL 把错误升级成异常；未修改原版着色器、uniform、求根器或许可逻辑。三帧均 `densityShaderFailed=false`，后两帧实际提交 20,000 点各一次。此前尝试 pbuffer 也已保留：本机工厂报告不支持，实际仍选择 FBO，不能称为成功的 pbuffer 验证。

## 为什么同一时间、同一种子不能直接定义参考图

原版 `ComplexRootsMobject` 构造函数即启动工作线程。`update` 和 `display` 会从队列接收批次，`displayDensity` 再按待绘制预算消费点。暂停场景时钟并不会冻结后台求根及批次到达。

本机原版实际创建 4 个工作线程；产品导入器明确告知源文件未指定的机器默认值无法恢复，本地采用 1 个逻辑工作器和确定性 ordinal 顺序。产品还明确暴露固定样本时钟、批次发布、待绘制队列及累计点数。这些事实不能仅用“seed 相同”消除。
