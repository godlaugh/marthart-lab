## 解决的问题

Roots 需要同时保留三份不同含义的状态：用户正在编辑的作品、上次完整应用的配置、当前显示中的热修改。此前运行路径会从每次请求的作品读取模式、相机、时间线和公式，导致“只换颜色”也可能带入尚未应用的其它编辑。录制开始需要回到上次完整应用的配置，停止时又不能把作者的暂存编辑覆盖掉。

新协议按明确动作改变状态，普通重绘不会自行应用作品内容：

| 动作 | 后端行为 |
| --- | --- |
| Apply | 保存完整已应用配置并重建；相同值再次 Apply 仍是新动作 |
| restart | 使用已应用配置重建，清除热修改，保留作者作品 |
| palette / tone / transform / camera | 只修改命令指定的运行字段，不带入暂存模式、相机或时间线 |
| 录制开始 | 从已应用配置重建，增加重置计数；保持外部命令的消费水位 |
| 录制结束、暂停截图、普通重绘 | 继续使用录制后的运行状态，不重放已消费的热修改 |
| 暂存编辑 | 作者作品可以变化；没有 Apply 或热命令便不改变运行配置 |

手动色板 offset 是明确保留的本地热修改政策，尚无原版独立 Inspector 控件的对应证据；运行中的渐变动画仍由动画状态管理其后续 offset。源色板热更新沿用原版 UI 颜色解析；空列表及省略值是热更新空操作，不等于冷配置的默认色板。

主线程 `RootsControlJournal` 保留按序命令；Worker `RootsControlOwner` 保存已应用配置、当前配置和消费回执。回执区分命令序号、最近 Apply 序号、重置次数。已执行但画面过时的命令也会被确认，避免重复执行；不同文档会话的回执没有修改新文档的权限。

命令先验证形状、序列和内存预算，再改变运行资源。预算计入共享对象展开后的表示、待处理命令、指纹和新旧快照；循环引用、序列缺口、伪造确认以及相同序号的不同内容会被拒绝。可保留旧预览的拒绝仍允许截图和录制。Worker 状态丢失时，只有确认序号的请求明确要求重新 Apply，不从作者的暂存内容悄悄重建。

录制和截图消费者改用实际完成帧的模式、动画、公式、相机及回执；队列停止回调会重新确认当前文档会话，避免同步切换文档后采用旧画面。旧版无 controls 的调用路径仍可使用。

真实主矩阵走公开 Generator → generation Worker → 真实计算 Worker → WebGL，固定一个采样 Worker、256 个样本、192×144 画面。两种模式各执行：应用 A → 热调色 B → 从 A 录制并结束 → 截图/重绘仍为 A → 再次热调色 B → Apply B → 从 B 录制并结束。作者作品同时含相反呈现模式、相机变化和 60 秒等待轨道，以检查这些暂存值没有泄漏。实际消耗的计算批次、完整 RGBA、准备后的 GPU 色表和回执都被保留。

本批的四段主矩阵录制是实际录制帧流，**没有编码 MP4**。六张 PNG 将实际返回的 RGBA 保存为图片，未经过 App 的导出按钮；同尺寸截图检查了原始画面经过实际增强步骤后得到交付图像的链路。没有证明任意尺寸截图、多 Worker 到达顺序、长时间动画或完整 App 录制。

损坏注入在真实数学计算和 GPU 渲染后修改传输信封，只证明客户端拒绝错误事实，不代表观察到外部故障。部分单元测试使用资源替身，其结果与真实 Worker 验证分开记录。

源码在最终运行前后摘要一致；浏览器、Vite 和记录中的 Worker 已清理。可重跑入口为 `scripts/verify-roots-control-owner.mjs` 与 `scripts/verify-roots-recording-transport.mjs`。

## 成本记录

在同一已预热 Chrome/Vite 中，分别使用新的 Generator/Worker 完成相同的 256 样本生成，再进行 32 次暂停重绘。比较的是当前源码中旧合同与显式控制合同，**不是两个完整历史版本**。33 帧 RGBA 序列和 8 个已消费 CPU 批次摘要全部相等；启动期间轮询显示次数受调度影响，分别为 36、33 次。

| 测量 | 旧合同 | 显式控制合同 |
| --- | ---: | ---: |
| 新 Worker 初始化至计算完成 | 491.2 ms | 484.6 ms |
| 32 次暂停重绘 | 72.6 ms | 81.1 ms |
| 测量区间总耗时（含观察及序列化） | 821.9 ms | 823.4 ms |
| 验证器进程族 CPU | 1.51 秒 | 1.52 秒 |
| 采样峰值 RSS | 2,093,872 KiB | 2,091,312 KiB |

每组仅一次，浏览器和 Vite 已热身，Worker 为新建；未清除系统/驱动缓存。CPU/RSS 以验证器 Node 进程为根，每 250 ms 采样其进程族，包含 Node、Vite/esbuild 和所属 Chrome，可能遗漏短命进程和瞬时峰值。被动摘要与序列化开销包含在测量中；没有单独分离各进程类别的成本，也未计 agent tokens、GPU 设备时间/显存以及启动准备成本，不据此宣称普遍加速。

## 验证中修正的旧预期与脚本

- 一条旧导入测试把 ProjectState 的默认色板误当作运行配置的省略语义。完整基线 `a131a3a` 独立检出后复现同一失败；按固定原版静态证据修正测试，分别检查项目入口的七种默认颜色、运行入口保留省略、空列表及单色保存重载。产品导入逻辑未因此改动。
- 首次新验证误把截图增强前 RGBA 与增强后交付图片直接比较；第二次误以 JSON 属性插入顺序判断命令相等。分别改为追踪真实增强链路、按字段和值严格断言，最终第三次运行通过。两次失败证据仍保留，产品没有为这些脚本误判调整。
- 新队列测试补全了原生 Roots 输入与输出类型，保留严格类型检查；没有移除失败用例。
