# 域着色旋转时钟：原版数值链差异复现

本轮已复现域着色动画时钟的实际差异，尚未修复。它不只是浮点精度问题：原版在动画队列活动期间，每帧更新域着色对象两次；当前本地版本使用连续积分计算角度。这个问题属于 2.0 效果一致性验收的 `MAS-DOM-026`。

## 实测结果

输入为一个 1 秒的 `LINEAR` 动画，将 `domainRotate` 转速从 0 变为 1。原版固定更新频率设为 4 fps，便于逐帧检查；本地通过真实文件导入器和生产 Generator Worker 渲染。表中按累计经过时间对齐，角度单位为弧度。

| 经过时间 | 原版 JVM 角度 | 当前本地渲染角度 |
| --- | --- | --- |
| 0.25 秒 | 0.125 | 0.03125 |
| 0.50 秒 | 0.375 | 0.125 |
| 0.75 秒 | 0.75 | 0.28125 |
| 1.00 秒 | 1.25 | 0.5 |
| 1.25 秒 | 1.5 | 0.75 |
| 1.50 秒 | 1.75 | 1.0 |

原版运行了 5 组、共 42 帧数值轨迹，包含固定步长、指定可变步长、暂停、队列结束和空队列。完整运行两次，输出完全相同。上表只比较第一组的 6 个对应时刻；其余轨迹保留供后续实现验证。

本地完成 7 个时刻的 79×53 CPU 图像生成；Worker 返回的角度与时间线求值相同。保存、冷启动重新加载后的 0.75 秒图像哈希也相同。因此，差异已经进入生产渲染输入，并非仅出现在测试辅助函数中。

## 根因与修复边界

原版 `DomainColoringScene.update` 先调用父类 `Scene.update`。队列在帧开始时仍活动，父类就会按受剩余时长约束的 `activeDt` 更新对象；子类随后在未暂停时，再按完整 `rawDt` 更新同一个对象。队列结束后的后续帧只执行第二次更新。每次旋转执行分阶段 Float32 乘法和加法。

当前 `timeline.ts` 的域旋转分支通过 `angularRotationDelta` 求连续积分，没有这两个独立的更新阶段，也没有原版队列逐帧消费规则。

修复需要由同一个域场景运行实例管理队列、旋转、参数和渐变，并让播放、跳转重建、导出使用它提供的帧状态。简单把角度乘以 2 会在队列结束、最后一帧剩余时长裁剪以及暂停边界产生错误。现有参数注册表采用独立的 60 Hz 重放；迁移时必须一并核对，不能与新的域时钟各自推进。

字节码显示，每次域对象更新内部先执行参数动画器（接收 `dt` 和宿主 `PApplet.frameRate`），然后更新渐变，最后累加旋转。两次对象更新必须分别经过这条链。完整 Apply 的源路由也需要区分：Domain 无论暂停或播放都重新加载场景；不能沿用分形暂停时只更新对象配置的分支。本轮未执行 Apply 界面操作，这一结论属于静态路由证据。

本轮没有修改生产行为，也没有将该项标为验收通过。后续实现应先覆盖上述原版数值轨迹，再验证参数和渐变活动时的调用顺序，最后接入公开播放和导出流程。

## 验证范围

原版证据实际执行了安装包中的 `DomainColoringScene` 构造、`JsonDomainColoringConfig.setupTimeline`、`SceneManager`、`DomainColoringScene.update` 和 `DomainColoringMobject.update`。

探针通过 JNI 分配并初始化了 PApplet、配置和域对象的必要字段；没有执行原配置或域对象的完整构造，没有运行 `construct`、绘制、OpenGL 或窗口。原参数和渐变动画器虽使用原构造函数，但本批保持未活动。因此，这批证据证明所列数值更新链的差异，不证明完整应用生命周期或图像一致性。

两次原版探针分别耗时约 1.079 秒、0.348 秒，均正常退出并回收；不是受控冷暖性能基准。浏览器和 Vite 服务已关闭。本轮无生产代码改动，未重跑全量测试或打包，也未修改已安装的 Apple Silicon 1.0 应用。

当前桌面检查仍返回 Mac 已锁定，未取得原版窗口截图，也未移动窗口或发送输入。2.0 仍处于 M3，11 类场景的原版整图对照通过数仍为 **0/11**。
