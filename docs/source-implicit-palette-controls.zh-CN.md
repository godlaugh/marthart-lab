# Implicit 色板与录制状态验收（2026-10-24）

后续界面接入和实际 PNG／MP4 验收已完成，见[调色界面记录](source-implicit-palette-ui.zh-CN.md)。下文保留本批后端验收时的范围。

本批完成源 Implicit CPU 网格的显式运行控制：编辑中的作者文档、当前热色板、最后完整应用的冷配置各自保留。开始录制会恢复冷配置，结束后保留作者草稿。**这是后端与公共生成／录制接口接入；App 的 Implicit 色板生成器界面尚未接入。**

基线为 `5dd5b8d4e6c8018ba5a8aa9bc338a7bde1e70f23`。原版依据来自固定 MathArt 1.7.8 JAR 的已校验静态证据，本批没有新增原版 JVM 或桌面窗口执行。源码摘要、原方法位置与验证记录见[证据索引](../tests/fixtures/source-implicit-controls/backend-20261024.json)。

## 为什么要区分这些状态

原版 `MathArtSession.updatePaletteOnly` 使用热解析器：八位颜色仅保留 RGB，并把 alpha 设为不透明；空列表不改变当前颜色。完整 Apply 经 `ProjectState.toJson → reloadConfig` 写入冷 JSON，冷解析器保留 ARGB，空色板显示白色。

工具栏录制回调先调用 `resetScene`，再启动录制；初始化读取最后的 `currentJsonConfig`，没有先序列化当前编辑器。因此把最新编辑值直接当作录制配置会带入未应用的修改，也会丢失冷颜色的透明度。上述结论是静态控制流推导，不能等同于本批观察了原版运行。

| 已应用 A、暂存草稿 B 后的操作 | 当前画面与冷配置 |
| --- | --- |
| 提交热色板 C | 只改变运行颜色；alpha 变为不透明后再乘填充透明度，冷 A 不变 |
| 提交空热色板 | 确认此事件，但保留当前颜色 |
| 再次提交相同 C | 仍是新事件；录制重置后可再次生效 |
| 重新开始 | 恢复完整 A，不把 B 自动应用 |
| 完整 Apply B，包括同值 Apply | 更新冷配置并重新开始；同值操作也执行 |
| 开始录制 | 从冷 A 重建；停止后保留作者 B，运行状态继续来自 A |
| 无效 Apply | 几何／公式验证失败时不提交命令；旧完成预览仍可录制 |
| 暂停后改色、截图 | 使用持有的数值帧，不推进动画 |

背景透明、网格、坐标轴也改为读取生成方交付的有效显示配置，避免绘图器从作者 B 读到尚未应用的值。原始色板单独保存在 `implicitSourcePalette.colors`；保存重开保持空列表、单色、ARGB 及无法解析的原始文本，颜色解析不会覆盖原文。未提供该字段的旧文档保留已有处理方式；本批未迁移旧导入器或界面。

## 协议与失败边界

公共输入使用独立会话、连续命令序号和确认水位，结果携带实际应用／重置回执。Worker、客户端、录制租约和生成队列共同校验；过期画面也先确认已执行事件，再保留后续待处理命令，避免重复执行旧热色板。录制前后保留草稿，录制期间排队的热修改随后作用于继续播放；排队的重启则明确新建数值状态。若同一作品对象已切换到新控制会话，旧录制结束不会再把自己的数值会话或画面交给新请求。

新会话必须从 Apply 1 开始。新 Apply／restart 请求要求 `time=0` 且不携旧 `implicitLive`；这里的请求零时刻不意味着原版首个显示更新的数值时刻为零。录制后继续绘制必须携带返回的数值会话；取消或丢失 Worker 后不能靠旧确认号恢复，需要明确 Apply。

普通预览准备、几何验证与录制 warmup 失败不会提交候选冷／热状态。继续播放若已消费数值更新后发生错误，沿用原有失败边界：旧数值队列不可继续，须显式重启。没有宣称所有失败都能原帧重试。

命令及保留状态沿用 768 MiB 表示预算，并在展开／克隆前检查；单份色板至多 65,536 项、1 MiB UTF-16 文本。这些是本地资源边界，不是原版限制或整个进程 RSS 上限。

独立无界面 Chrome 实际经过公共 Generator、真实 Worker、CPU 几何、WebGL 录制及暂停截图接口，**605 项检查通过**：

## 等价工作量成本

现有无控制协议路径与新增控制路径，在同一版本中各使用一个新 Worker，完成首次生成及八次重绘。两边九帧完整几何摘要序列一致。

| 路径 | 新 Worker 首次生成 | 随后八次重绘合计 |
| --- | ---: | ---: |
| 无控制协议 | 298.6 ms | 35.0 ms |
| 显式控制协议 | 358.4 ms | 36.8 ms |

这不是两个 Git 版本的统计基准。浏览器及模块缓存已热，每种路径只顺序运行一次，计时包含散列开销，不能据此声称提速或稳定性能回退。整个实际验证耗时 4.263 秒；其中采样区间 3.118 秒，进程族 CPU 14.210 秒，采样峰值 RSS 1,818,640 KiB（约 1.73 GiB），包含 Node／Vite／Chrome、复制与观察器。单独变体 CPU／RSS、Agent tokens、GPU 时间／显存及遗漏的瞬时峰值未测。
