# Symmetry 有序更新调度修复验收

2026-10-21。已修复漏掉原版 Symmetry 场景额外更新的问题。队列进行中按顺序执行两次粒子更新，空队列或完成后的未暂停帧仍执行一次，暂停时不更新。每次更新使用自己的参数快照，随后只显示一次。

该修复已进入本地预览、定位和导出共用的生成路径。**原版整窗口效果验收仍为 0/11；新增实时编辑重播的 Worker/编辑器接入仍未完成。** 已安装的 1.0 Apple Silicon 应用没有重新打包或替换。

## 根因和结构修复

[原版 JVM 调用证据](source-symmetry-dispatch-correction.zh-CN.md)证明，实际类 `GenericSymmetryChaosScene` 在通用 `Scene.update` 返回后还会更新对象。此前只使用通用路径，导致更新次数不足，并错误地在空队列或完成后停止演算。

时间线所有者现在保留有序的 time、dt 和参数快照，参数及渐变按每次调用推进。通用相机更新后提供一个可选钩子，只有 Symmetry 使用它；其他场景的更新逻辑不变。旧的布尔更新事件已经移除。

GPU 依次执行各快照对应的数学场，预热只使用第一次更新的参数，之后一次显示。不能把迭代次数简单乘二并统一使用最后的参数。每帧配置、相机和调色板只解析一次，逐次更新只重新准备数学场。两次调用的数学错误计数累加，进入下一帧时清零，避免第二次调用覆盖第一次的失败记录。

独立编辑重播执行器也接收有序字段；正常更新先执行，显示重播再按既有预算执行。开始重播时重新取保存的种子，后续帧仍执行正常的两次更新。此执行器目前通过独立 GPU 驱动验证，尚未成为界面实时编辑的调用路径。

## 实际验证结果

| 验证 | 结果与范围 |
|---|---|
| 原版调用记录对照 | 9 例、45 帧的次数、时间、dt 全部精确匹配，包括暂停、pending、replayActive |
| 针对性测试 | 5 文件、70 项通过；包含独立参数快照、确认阈值、渐变持续更新、冷启动/回退一致性 |
| 全量测试 | 338 文件、6,223 项通过；最后的数学场准备精简后另跑公开操作与 TypeScript/Web 构建 |
| 实际 WebGL 帧计划 | 内置 buffer 和自定义 texture 两种存储均通过；包括空/零/短队列、显示不演算、无效值、两次调用的错误计数及清理 |
| 有序参数 GPU | 12 帧逐粒子 Float32 结果与独立计算相等；两次不同参数依序生效，预热只算一次；3 类公开生成用例通过保存重开和回退检查 |
| 编辑重播 GPU | 6 个原有场景、219 个重播帧通过；新增 3 帧不同参数双调用通过，包括重播开始时丢弃旧轨迹和随后继续更新 |
| 实际 App/Worker | Map、Symmetry 的导入、编辑、播放暂停、定位、保存重开、PNG 与 MP4 全部通过，无 App/Worker 错误 |
| 导出 | PNG 与对应 Worker 像素逐通道比较；视频每例 3 帧、3 FPS、192×128，上传帧像素与 Worker 对照并核对 FFmpeg 输出元数据 |
| Web 构建 | TypeScript 与 Vite 通过；保留已有大 chunk 提示 |

测试纠正了两类旧假设。每帧两次很小的参数变更可能合计超过显示清空阈值；只检查单次变更会漏掉。另一个旧用例在本地时间线总时长之后取样，受到编辑器时间范围截断，曾把重复采样误判为原版停止演算；现在将本地总时长设置得长于源队列，明确验证队列结束后的运行帧。

首次参数 GPU 用例在第 10 帧碰到所选自定义公式的逃逸半径，不能再用单纯加法作为期望。已为该小型加法用例显式设置足够大的半径，并验证粒子位置；没有放宽比较精度。最终核对逐 Float32 值完全相等。

## 留存结果和测量边界

本地完整输出均在 `.cache/source-symmetry-replay/`：

- `dispatch-frame-gpu/report.json`：帧计划和错误计数。
- `dispatch-parameter-final/report.json`：有序参数与公开生成。
- `dispatch-replay-gpu/report.json`：编辑重播、双参数调用和取消恢复。
- `dispatch-public-final/report.md`：可阅读的公开操作结果，同目录保留截图、PNG、项目和 MP4。
- `dispatch-focused.log`、`dispatch-full-tests.log`、`dispatch-build-final.log`：测试和构建日志。

这些结果不进入 Git；复验脚本及本说明进入 Git。每次 GPU/公开操作运行都核对运行前后的源文件摘要一致。

| 完成任务 | 总耗时 | 采样 CPU 时间 | 采样进程族峰值 RSS |
|---|---:|---:|---:|
| 帧计划 GPU | 2.41 秒 | 6.28 秒 | 1.37 GiB |
| 有序参数 GPU | 2.39 秒 | 6.12 秒 | 1.37 GiB |
| 编辑重播 GPU | 34.52 秒 | 7.87 秒 | 1.42 GiB |
| 最终公开操作 | 13.38 秒 | 26.55 秒 | 2.17 GiB |

每项是新启动浏览器的完整任务，内部包含同一会话的持续帧和回退重建；未独立分离系统缓存冷/热运行。编辑重播测量与全量测试有并发，耗时受争用影响。65,536 粒子、640×480 的代表重播子任务完成 30 帧、100 次累积、13,107,200 次数学步，约 0.954 秒。

CPU/RSS 按 250 毫秒采样；CPU 是观察到的累计下界，RSS 可能重复计入共享页并漏掉短暂峰值，短任务中未另行消除 PID 复用影响。GPU 实际内存、单任务 agent token 未测量。本次调度修正改变了有效工作量，没有等价的旧实现性能基线，不据此声称性能提升。

## 尚待完成

原版 JVM 证据只执行场景、队列和相机更新，并用计数子类替代 Mobject.update；它不验证原版参数动画与 JOGL 粒子轨迹的联合执行。GPU 对照使用本地 WebGL 和独立计算，也不等于原版窗口像素对照。

下一步是将实时时间线所有者、编辑重播与相机确认接入 TemporalGenerationSession/Worker/编辑器，并补齐尺寸变化时的资源生命周期。完成后再进行原版整窗口对照。当前 Goal 保持进行中。
