# 吸引子原生绘制与导出验收

源 CPU 吸引子已接入本机原生 OpenGL 绘制，预览和图片、视频共用相同的分块绘制路径。每帧使用一个绘制目标，依原顺序提交完整粒子与轨迹，读回后确认释放。不会通过减少粒子、缩短拖尾或改用其他渲染器来通过验收。

这项工作属于 2.0 的效果一致性阶段，尚不代表整个吸引子场景或 2.0 已验收完成。

本记录对应 preview.11 的原生接入阶段。随后 preview.12 已完成有限输入的原版公式与完整数学＋公式图层验证，详见[吸引子原版公式验收](source-attractor-formulas-validation.zh-CN.md)。

## 已完成的原版对照

原版 1.7.8 自带的 Aizawa 和 Dadras CPU 预设均保持原输入。独立运行原版完整时间线共 4,964 次更新，在 27 个关键节点比较全部坐标、颜色、时间和 FIFO 轨迹，2,304,900 条历史记录一致。

最终 4 MiB 分块原生路径重新对照同一批原版数学画面：27 张完整 500×600 图像，共 8,100,000 个像素，差异为零。节点覆盖时间线动作、完成帧及完成后的下一帧。比较边界是原版数学图层，不包含公式、水印和增强处理。

## 已完成的实际操作

两份原版预设分别在像素密度 1 和 2 下，通过实际应用界面完成了 110 项检查，包括：

- 原生预览、PNG、JPEG 和短 MP4 导出。
- 请求 503×607 时，密度 2 对齐后的实际 504×608 尺寸正确显示并交付。
- 原生分块已提交时取消，释放资源后再次成功导出。
- 在吸引子与碰撞场景之间切换，正确释放各自持有的原生状态。

上述检查的浏览器、Worker 和原生服务没有报告错误，服务退出后没有遗留自有进程。全部使用无头浏览器，不操作用户桌面。

同时修复了以下实际问题：CPU 生成结果遗漏公式呈现信息；在分块确认尚未返回时卸载预览，把正常等待误报为清理失败；时间线静态提示误执行同步粒子预热，使合法 Dadras 的播放按钮被旧预算禁用。时间线现从已有解析器取得静态队列诊断，真实粒子与跟踪状态继续由生成器负责。公式仍采用现有 MathJax 路径，不能据此声称与原版公式图像一致。

桌面重启时还复现了取消与清理的竞态：浏览器已经取消旧请求，服务端仍在收尾，立即释放会收到忙状态。清理重试仅适用于服务端明确标记的暂时忙响应，仍持有原资源身份和本页事务；其他容量、归属和清理错误不会被掩盖。

## 桌面包与共享功能

已生成 Apple Silicon 本地 `2.0.0-preview.11` 应用包，并通过 `codesign --verify --deep --strict`。在隔离配置的隐藏 Electron 中，原版 Dadras 完成导入、实际前进一帧、回到起点、96×80 原生 PNG、保存、退出和重启。同样对齐到起点后，两次 PNG 的完整 RGBA 哈希一致。两个应用进程组均已退出，服务端口关闭，没有窗口显示事件。

首次验收保留了时间线校验错误；随后两次尝试分别暴露 Electron 调试协议响应体不可取和取消清理竞态。验证器现在旁路复制真实响应，始终返回原响应，不让观察断言改变产品流程；最终以第四次完整运行作为通过记录。

共享图像导出的隐式曲面回归通过 320 项检查，包含真实调色板控件、PNG、两段 MP4 和进程清理，源码在运行期间未变。这是本地功能回归，不扩大原版画面对照范围。

## 高配视频与编码核对

测试输入为 2000 粒子、每帧 10 子步、10 秒拖尾、200 次预热，目标为 1080p、30 FPS、10 秒，共 300 帧。拖尾上限达到 1,440,000 条，完整几何可以在本地预算内进入分块计划。

最初每块上限为 1 MiB，满轨迹帧需要 137 块。本轮实际测试在 20 分钟验收时限内完成并接受了 264 帧，没有原生 HTTP 错误，但未交付完整视频，记录为失败。退出时浏览器、服务和编码器已清理，源码在运行期间未改变。

现在默认及硬上限统一为 4 MiB，并按保留几何、完整绘制目标和传输副本的联合预算自动缩小。相同高配帧由 137 块减少到 35 块，14 组属性数据流的完整哈希不变；表示预算峰值 261,007,444 字节，低于 256 MiB。单独 CPU 打包测量没有明显提速，减少的是 102 次追加请求。

验证脚本也移除了为每个大请求建立 Playwright 响应对象的监听，改为浏览器内汇总计数；这部分属于验证器开销，不能全算为产品加速。上限组合已实际交付完整 300 帧，导出耗时约 23.1 分钟。前 264 张 PNG 与旧分块路径逐字节相同；四个新建连续生成器的重放检查点也与交付 PNG 完全一致。分块数量虽减少，实际高配绘制仍慢，不能声明视频导出明显加速。

旧脚本使用 PNG 与有损 H.264 的平均 RGB 误差小于 6 作为门槛，在第 197 帧遇到 6.94 而失败。进一步核对确认这是通用 MP4 的有损结果：以全部已保存 PNG 解码出的 RGBA 为输入，使用实际 `medium / CRF 18 / yuv420p / threads=2` 独立编码，300 帧解码 RGB 全部严格相同，两个 MP4 文件也逐字节一致。原失败记录保留，新的验收使用独立编码全帧对照，不通过放宽误差容限来判定成功。

这里的“高配”指粒子和拖尾负载，不等同于应用的 MathArt 高质量编码档。下限组合也已完成相同回归。两份视频均为 300 个不同画面，逐帧非空门槛保留：下限／上限每帧最少分别有 3116／3977 个不同于该帧背景的 RGB 像素。独立连续重放的第 0、49、149、299 帧 PNG 全部相同。

| 项目 | 下限组合 | 上限组合 |
|---|---:|---:|
| 粒子／子步／拖尾秒数 | 1000／5／5 | 2000／10／10 |
| 最终历史记录 | 420,000 | 1,440,000 |
| 生成至视频下载 | 436.88 秒 | 1385.13 秒 |
| 原生请求数 | 3,861（含重放） | 10,203（原导出阶段） |
| 采样进程族 CPU 累计 | 1291.26 秒 | 4144.07 秒 |
| 采样进程族 RSS 峰值 | 4,897,328 KiB | 5,659,728 KiB |

下限整次验收耗时 464.76 秒。上限原运行在旧阈值处停止验收，之后复用同一交付文件做独立编码和四帧重放；不能将它描述成单次完整性能基准。CPU/RSS 包含验证器，RSS 相加会重复计入共享内存；250 ms 采样可能漏掉短进程和峰值。GPU 显存、后验检查的进程族成本和整个代理任务的 token 成本未测量。
