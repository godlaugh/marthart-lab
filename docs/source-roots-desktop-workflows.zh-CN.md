# Roots 桌面录像、尺寸变化与取消恢复验收（2026-10-27）

`2.0.0-preview.15` 的 Roots 点云已补验实际视频导出、窗口尺寸变化、跨场景返回和取消后恢复。原版同一段动画的 36 次更新与产品的时间、相机及渐变状态逐位一致；**独立运行的最终画面仍有差异，未声明整段录像与原版逐像素一致**。本轮只改验证器与记录，没有修改或重新打包产品。

## 实际通过的工作流

| 工作流 | 结果 |
|---|---|
| 完整数学控制 | 原有空时间线输入完成 131,072 次采样、4 个 Worker、1,310,720 个根点，导出当前 PNG |
| 尺寸变化 | 暂停状态调整尺寸，保持同一实例和场景时间；恢复尺寸后的完整数学 RGBA 与变化前相同 |
| 跨场景返回 | Roots → Spirograph 释放原资源，再导入 Roots 完成全量求解 |
| 动态录像 | 实际生成 35 帧 MP4，96×80、4 fps、8.75 秒；相机及渐变确实变化 |
| 取消 | 两帧上传获确认后点击 Cancel；允许已经发出的第三次数值帧完成，随后清理导出任务 |
| 取消后恢复 | 同实例继续播放，再导入完整控制输入完成全量求解并导出 500×600 PNG |
| 窗口与退出 | 两次执行均无可见窗口或 show 事件；应用退出码 0，自有进程组为空，端口关闭 |

录像输入只替换原有有界控制的时间线，保留采样数、batch 32,256、4 个 Worker、seed 0、公式、点径及其它配置。构造时间线为 ambient、zoom、gradientStart，等待，stopAmbient、gradientStop，再等待；总场景时间 9 秒。首个更新是预热，后续 35 次更新成为编码帧。完成判断使用真实动画队列，不能因为求根尚未耗尽而自行增加帧；本次恰好在队列结束时也已完成全部根点。

## 录像验证范围

实际请求 96×80 输出，录制中间画面为 288×240。验证器逐帧绑定正式原生 finish 返回、Worker 图像、实际公式合成结果与上传 PNG，完整 RGBA 相同。随后读取真正下载的 MP4，另把这些原始 RGBA 交给同一 FFmpeg 编码配置，通过独立 rawvideo 输入编码，逐帧解码比较：35 帧 RGB 差异通道数均为 0，共有 32 张不同的解码画面。

交换两个不同输入帧或重复首帧会被比较拒绝，因此检查不只是“视频能打开”。H.264 为有损格式，这里没有声称解码 RGB 等于未压缩输入，也没有把独立 rawvideo 编码称为原版 MathArt 的录像。

## 取消检查的修正

第一轮整体状态保留为失败：脚本收到数值 `source-recording-finish` 后立即检查 HTTP DELETE，此时界面仍在执行 catch/finally 清理。此前已经完成的尺寸变化、切换和 35 帧视频证据有效，但不能把第一轮整体标成通过。

验证器改为等待公开的 Close export 按钮重新可用，再冻结结果检查清理终态。第二轮用 `--workflows --phase cancel` 仅重跑完整控制、取消及恢复，没有重复无关的 35 帧视频。

第二轮实际上传获确认 2 帧、产出 3 个编码候选数值帧；取消后的 finish 保持实例 2、数值帧 4、场景时间 1 秒，没有额外推进。HTTP DELETE 返回 200，没有 finish 请求、下载或保存的部分影片；随后同一实例实际续播。恢复控制完成全量求根与当前 PNG，导出临时文件为空。历史报告的 `actualEncodedFrames = 2` 在取消分支仅代表成功上传数，不代表保存了两帧影片。

## 与原版动画的比较

原版使用相同输入字节、4 fps、主画布逻辑 862×553、DPR 2、参考高度 553，录制目标逻辑 144×120／物理 288×240。正常权限与原版 Scene 执行保持不变，全程无窗口；未调用原版录像器或 FFmpeg，只采集其逐帧画面及按已核验预热规则划分的编码候选。

36 次更新的场景时间、队列位置与完成状态、相机和角速率、渐变的 running/progress/speedScale/targetSpeed/offset 全部逐位一致。原版在第 36 次更新、场景时间 9 秒完成队列，另取两个暂停帧保持稳定；38 张原 PNG 的解码 RGBA 与实际 loadPixels 完整一致。

另以实际 Worker 的 presentation、场景和渐变状态经过正式共享 producer 与 v15 codec，重建每帧 begin 请求；36 份完整 packet SHA 均与实际提交记录相同，绑定了真正发送的 shader 输入，而非另造参考值。再与原版比较：每帧 13 个数值 uniform（含矩阵）的 Float32 位与 1,024 字节 LUT 全部相同。sampler 明确从原版 unit 1 绑定到产品 unit 0，不声称它逐位相同。这项补验仅使用 CPU，没有重新运行 GPU。

独立并发求根的到达时刻不同：原版预热时已绘制 419,380 点，产品预热时为 0。全部 36 次更新的数学 SHA 不同；最后一帧双方均有 1,310,720 点，数学加公式完整图仍相差 **14,732 像素／26,687 字节，最大通道差 8**，其中 alpha 也参与比较。没有忽略差异、设容差通过或反向注入原版点流。既有[同到达顺序渲染诊断](source-roots-point-native-integration.zh-CN.md)与本轮自然运行属于不同证据范围。

动态 shader 输入一致不代表全部画面差异都由到达顺序造成；此前已记录的求根近零数值差等范围仍保留。

原版实际 JVM heap 为 512 MiB，产品保留其公开导入默认的 4 GiB 参考 heap。差异明确记录，未改输入去伪装相同预算；本有限输入没有证明两者在大负载下等价。新原生点云的实际 300 万最近窗口、1,000 万 ring 回绕、默认 4,755 万采样及原版同实例 resize 配对仍未验证，Roots 整族和 2.0 Goal 保持进行中。
