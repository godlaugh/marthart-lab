# 域着色录制状态管理验收（2026-10-22）

域着色的持有会话现已具备“开始录制 → 逐帧渲染 → 停止并恢复主预览 → 继续播放”的底层能力。此次没有连接 Worker、任务队列或 App 的录制入口，不能据此宣称用户界面的域着色录制已经完成。原版整窗口效果一致性验收仍为 **0/11**。

录制从最后一次完整 Apply 的配置重新开始。之后的热参数修改、暂停平移，以及尚未 Apply 的公式草稿不会混入录制；结束时保留用户草稿。新录制使用新的数值宿主和渲染失败状态，预热帧成功前保留此前已完成的主预览。

模拟时间使用录制帧率；参数动画另行接收每一帧的实际观测帧率。两者不能混用。录制先执行一次预热更新与渲染，预热图不计入待编码帧；空队列也只有这一帧。内部绘制尺寸沿用输出尺寸乘三、再按父画布像素密度取整的规则。

停止录制只重置墙上时钟并重绘当前状态，不再推进数值。停止重绘失败后可以重试，重试不再重置时间。某帧数值已经更新但渲染失败时，保留该数值快照：重试必须提供同一已消费帧率，不会重复更新参数。取消后仍可执行停止清理；正常录制期间拒绝实时编辑和释放。

旋转、转速、场景时间、原始时间间隔和色板偏移按 Float32 位模式核对留存的原版 JVM 样本；参数 a 按既有的数值容差核对，参数 b 精确比较。本轮没有重新执行原版 JVM，也没有与原版 JOGL 像素比较。浏览器测试使用保存样本中的观测帧率作为显式输入，尚未实现界面中的实时帧率观测来源。

此次还移除了队列时长规则的重复解释：数值运行时、时间轴布局和录制规划共用同一个时长函数。录制规划只确定队列结束序号，不预演参数动画，也不保证未来每帧渲染成功；真实宿主的录制序号与完成状态逐帧检查。它保留原有的 200 万工作预算和 24 小时边界。

完整浏览器验证的进程族采样记录为：墙上时间 **2.30 秒**，观测 CPU 时间 **6.44 秒**，峰值聚合 RSS **1.40 GiB**，结束后未观测到遗留的所属进程。50ms 间隔采样可能漏过瞬时峰值；共享页可能重复计入 RSS。没有等价的改动前基线，未把冷/热完整任务分开计时，也未测量完整 token 成本和显存，因此不作性能提升声明。

可复核入口：`scripts/verify-source-domain-recording.mjs`；本机原始结果为 `.cache/domain-recording-owner-measured/report.json`、`.cache/domain-recording-owner-measure.json` 与 `.cache/domain-recording-owner-full-tests.json`。浏览器验证前后源文件哈希一致。本轮使用无界面 Chrome，没有向用户桌面发送鼠标或键盘输入。

下一步需要让 Worker、客户端和任务队列明确传递每帧观测帧率、维护失败后的录制句柄，并验证传输重试与停止恢复。之后再连通 App 的域着色实时预览、Apply、热参数、当前 PNG 和录制入口，执行实际导出验收。原版整窗口对照还需要先验证虚拟屏上的目标截图和输入能力。
