## 操作后的行为

| 操作 | 界面与运行状态 |
| --- | --- |
| 修改显示模式、Inspector 相机、时间线 | 保存为作品草稿，提示有未应用修改；当前动画继续使用已应用配置 |
| 点击“应用场景” | 应用完整当前作品并重新开始；相同值再次点击也执行；暂停时保持暂停 |
| 提交数学/采样/过滤/颜色度量 | 明确应用完整场景，包含当时其它已暂存的编辑 |
| 修改源色板、亮度等调色、空间变换 | 只提交对应热修改，保留其它暂存编辑 |
| 暂停后拖动或滚动画布 | 从实际呈现帧的相机起算，只修改运行相机；不改 Inspector 作者值，也不新增作品撤销项 |
| 返回起点/重新开始空间采样 | 重新运行上次完整应用的配置，并恢复播放；不提交草稿和热修改 |
| 开始录制 | 使用上次完整应用的配置；结束后保留作者草稿，并接收实际录制后的运行状态 |
| 保存、重命名、网格/坐标轴开关 | 不应用暂存的运行参数 |
| 从作品库切回 | 恢复该打开作品的冷配置及有序热修改；暂存草稿仍保持暂存 |
| 明确重新打开文件或创建副本 | 新建独立运行会话，从该文档初始化 |

原版静态证据确认了显示模式、相机角度以及已检查时间线操作的暂存行为。对本地扩展的相机中心、焦距、时间线子字段采用同一暂存政策；资源预算、点云拖影、预览方式切换等本地选项采用明确应用政策，不把这些扩展宣称为原版控件逐项对照结果。

## 历史与恢复

撤销记录同时保存作者文档和明确的运行事件边。撤销/重做暂存或元数据编辑时不改运行配置，即使期间发生过录制重置，也不会把旧热修改恢复出来。撤销/重做运行编辑时，新建会话、应用历史冷配置并按序重放其热命令；这恢复配置，不恢复旧墨迹、计算进度或时钟位置。这是明确的本地历史政策。

运行相机手势从已呈现帧读取有效角度和缩放。连续拖动可以累计已接受但尚未呈现的输入；播放切换、应用、重播、录制重置、会话或作者身份变化会终止旧手势。原版鼠标加速度与事件粒度没有在本批测量。

被拒绝的命令不会一直挡住后续修复：能够保留旧画面的失败仍保留该画面，下一次明确“应用”会建立新的命令会话。Worker 丢失、取消计算或初始化失败后也要求明确应用。无有效运行状态时撤销修复不会自动把作者值当作已应用配置。

打开文档先准备目标会话，成功后才替换当前状态。Roots 的命令、历史和作品库运行缓存共同检查 768 MiB 表示预算；按引用去重 owner/checkpoint，并在修改前为候选快照保守预留空间。预算不是整个 App 的进程内存上限，也不是实测 RSS；超限会拒绝本次操作，保留现有作者与运行状态。

## 验证记录

已运行 67 个文件、1587 项回归测试；累计预算补充后，相关 3 个文件、37 项测试再次通过。最后两处色板说明调整后，2 个文件、32 项控件与投影测试通过。构建通过，最终翻译检查无必需 UI 缺项；构建仍报告已有的大 chunk 提示。后两组是针对补充修改的复验，不与前面的测试数重复相加。

实际 App 已通过 **243 项检查、两种显示模式、6 张 PNG 和 4 个 MP4**。测试调用公共控件、真实 GenerationQueue、计算 Worker、WebGL 与 FFmpeg；使用隐藏的独立 Chrome，没有操作桌面窗口。运行前后 564 个来源文件摘要一致，没有未处理 App 错误，观察到的 Worker 和所属服务进程均清理为零。

两种模式均验证：暂存显示方式、相机和时间线后，热改色及调色只影响对应运行字段；直接录制仍从上次已应用配置 A 开始；明确应用草稿 B 后再录制才使用 B；相同值的再次应用仍执行。每轮录制后保留作者草稿，并可继续操作和导出 PNG。密度模式还实际验证了撤销/重做、保存、作品库切换、暂停时鼠标导航和同值默认色板操作。

6 张 PNG 的完整 RGBA 与实际截图输出一致。4 个 MP4 的每一张上传 PNG 都逐字节对照对应 Worker RGBA，**包括点云原有透明度**；所有视频解码 RGB 又与相同原始帧独立输入 FFmpeg 得到的参考编码逐通道一致，帧错序或重复会使校验失败。有损 H.264 与未压缩输入不作无损相等断言。密度两段各 12 帧，点云两段各 7 帧，均为 12 fps。

该矩阵固定单计算 Worker、256 次采样、512 个根；预览及编码输入为物理 480×360，MP4 输出缩放到 160×120。它没有覆盖任意尺寸的采样截图、多 Worker 到达顺序、长动画、公式标注合成或原版整图效果。工具栏重播和“非法 Apply 后修复再应用”的 App 流程本轮未实测；相关重启/保留/恢复规则有单元及后端证据，不能替代界面验收。

## 等价工作量成本

完整基线 `d6bf8dd` 与当前源码使用各自完整源码、独立浏览器及相同现有依赖。固定初始完整图像，再执行六次公共改色操作；两边 7 张完整 RGBA 的摘要序列、8 个实际 CPU 批次的字节摘要与计数完全一致，暖阶段没有重新采样。该成本矩阵实际呈现尺寸均为 479×360，与上面的录制矩阵分别记录。

CPU/RSS 取验证器 Node 进程族，包含 Vite、Chrome 与观察器开销，不能解释为应用单进程净成本。每个版本仅顺序运行一次，同一个 Node 进程，未清除系统、模块或驱动缓存；归档、服务及浏览器启动在计时阶段之外。因此“首次进入”不等于严格冷缓存基准。当前版本在本次观测中 CPU 与内存更高，未证明性能改善，也尚不能据此归因为稳定回退。Agent tokens、GPU 时间/显存和采样间隔遗漏的瞬时峰值均未测量。

独立正确性矩阵另耗时 32.219 秒，其中工作流测量 31.448 秒、进程族 CPU 62.140 秒、采样峰值 RSS 2,453,696 KiB；包括真实 FFmpeg 导出及独立参考编码，不能与六次改色基准直接比较。
